# 架构遵循

## 确定适用边界

按本次范围提取实际约束：模块责任、允许的依赖方向、公开接口、数据归属与访问入口、事务及一致性要求、权限和失败路径、兼容与运行限制。只记录会改变实现选择的项，保留来源和有效范围。

既有项目先定位相关路径和架构检查。没有文档时，结合仓库约定与已有合法能力形成局部实现说明，不默认套用分层、DDD、微服务或新框架；无法确定的重要边界按[输入规则](../shared/input-and-evidence.md)处理。

## 实现前后核对

| 关注点 | 可检查问题 |
|---|---|
| 职责 | 业务规则是否落在约定责任模块，是否在入口或展示层复制规则？ |
| 依赖 | 调用方向是否合法，有无循环依赖、跨边界读取内部状态或绕过公开入口？ |
| 数据与权限 | 是否绕过既有服务、存储、授权或事务机制，改变原子性与数据含义？ |
| 契约 | 输入输出、错误、事件和持久化结构是否符合当前要求，必要兼容和迁移是否覆盖？ |
| 失败与运行 | 失败后果、重试、资源和外部调用是否遵守当前约定？只检查本次相关机制。 |

优先运行已有模块边界、类型、依赖、契约或集成检查。对高价值且可确定验证的新增约束补自动检查；不要为每个文件建立与实现同构的断言。人工核对记录具体位置与理由，不把“已检查架构”当作证据。

测试替身可隔离外部系统，但应保留受测边界的真实语义。绕过权限、服务或事务的替身结果，不能证明这些约束成立。某条路径更短或现有测试变绿，不豁免有效架构要求。

## 复用与架构冲突

先判断问题是缺少合法接口、职责不合适还是复用候选本身不适用。可在授权范围内扩展公开能力、组合或适配；不能为复用反转依赖，也不能默认全局重构。允许有依据的新建实现，不追求表面统一。

需要改变有效架构时，说明不能承载的需求、影响和替代方案。用户已经明确委托架构调整时完成必要的局部设计与验证，不再次索取同一授权；未定业务或兼容取舍只阻塞相关部分。决定生效后同步关联说明、检查与迁移安排，不只在结尾追加风险。
