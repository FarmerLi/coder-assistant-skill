# 测试驱动开发

测试应能区分满足契约的实现与相关错误实现。测试数量、代码覆盖率和一次绿色结果都不能单独证明用例质量；重点检查预期是否有依据、是否经过目标边界、断言能否发现错误，以及执行是否可靠。

## 选择切片和测试边界

从有效验收选择一个能观察结果的行为，定义正常路径及相关边界、拒绝或失败后果。用例粒度由契约与风险决定：纯规则可单测，公开接口用契约或集成测试，关键用户流程按需端到端验证。不默认每个函数一个测试，也不把文件覆盖率当作验收覆盖。

选择能发现目标缺陷的最小测试层级。规则单测不证明接口接线、序列化、持久化或外部契约正确；本次改动涉及这些边界时，补充经过相应真实路径的测试。相同规则不必在每层穷举，但不能所有层都用替身绕过同一个待验证边界。

先识别项目测试入口、数据和环境，复用既有框架与测试工具。运行相关既有测试获取必要基线；已知失败、执行版本与环境如实记录。不要为了小任务引入另一套框架。

## 从契约推导用例

先核对有效需求、接口契约或已确认的缺陷事实，再确定预期。现有实现和测试可帮助理解现状，不能独自决定正确答案；材料冲突时按[输入与证据](../shared/input-and-evidence.md)处理。预期不清且影响业务取舍的部分保持待决，无依赖部分继续。

每个用例应能说明：验收来源、初始状态与输入、触发动作、预期结果和必要副作用，以及它要防止的错误。可直接体现在测试名、准备／执行／断言结构和少量注释中，不强制另建用例文档或编号。一个用例围绕一个行为场景，可用多个断言证明该行为的完整后果；不同前提或失败原因应拆开，便于定位。

按本次契约与漏检后果选择相关维度，不机械套用全部行，也不穷举无意义组合：

| 维度 | 有区分能力的用例选择 |
|---|---|
| 正常行为 | 覆盖有不同业务结果的有效输入或状态，而非只选一个最容易通过的样例 |
| 边界与等价类 | 在适用的阈值两侧及恰好等于阈值处取值；区分空、缺失、零、单项与多项等不同语义。长度、时间和金额按契约的单位及精度取边界，不随意使用浮点偏移 |
| 拒绝行为 | 对适用的非法输入、资源不存在、越权和非法状态，检查具体拒绝结果及禁止发生的副作用；权限规则有正常获准的对照，防止“全部拒绝”也通过 |
| 依赖失败 | 选择与本次约定有关的超时、异常或部分失败，验证错误传播／转换、回滚、补偿或重试后果，不只验证异常被抛出 |
| 状态与重复操作 | 检查状态迁移前后、重复请求、顺序影响及无关对象是否保持不变；幂等要求需验证业务副作用不会重复 |
| 并发与一致性 | 存在竞态、事务或唯一性要求时，构造可控制的交错或冲突，检查最终状态与不变量；串行调用两次不能证明并发正确 |

参数化用于相同规则下的不同输入，给每组数据可辨识的名称；不要把无关行为塞进巨大的参数表。共享规则变化时检查本次受影响调用方的差异，避免只覆盖新入口。覆盖率可帮助定位遗漏，但是否补用例由未验证行为与风险决定，不为指标写无效断言。

## 断言和测试数据

- **预期独立于实现。** 使用契约样例、可人工核算的字面值、独立初始数据或有依据的参考模型。不得调用受测算法或复制其分支逻辑计算预期，否则同一错误会同时进入实际值和期望值。
- **断言完整的可观察后果。** 按契约检查返回值、结构、关键字段、错误类型／错误码、持久化状态和必要外部副作用。不只断言非空、真值、状态码或“调用过”；也不无依据锁定私有方法、内部调用顺序、完整错误文案或未约定的排序。浮点容差、忽略字段和无序比较均须符合契约，不能遮蔽金额、精度或顺序错误。
- **失败路径也检查状态。** 明确哪些写入、事件或外部操作不得发生，必要时与操作前的独立快照比较。只断言抛错可能漏掉“先产生副作用再报错”。只包围目标操作捕获预期异常，不用宽泛捕获吞掉准备步骤或断言失败。
- **数据能暴露目标错误。** 若要验证筛选或归属，准备目标与非目标对象；若要验证排序，输入不能恰好已有序；若要验证累加或映射，使用可区分的多项数据，避免全零、相同值掩盖漏项或串值。断言预期不与可变夹具共享同一对象而随实现一起变化。
- **异步结果实际完成后断言。** 等待异步操作和预期拒绝，确认断言实际执行；不要让未等待的任务、回调或后台异常在测试结束后才失败。快照仅用于适合整体比较的稳定输出，更新前核对具体差异和需求，不能批量接受当前输出来消除失败。

## 测试替身与执行可靠性

测试替身只隔离非受测部分，不替换目标行为、关键规则或本次必须验证的真实边界。使用替身时，返回和失败形态遵守依赖契约；验证结果和必要交互，不以“mock 按配置返回了同一个值”证明业务正确。调用次数、顺序或参数只有属于契约（如幂等副作用、协议或参数转发）时才作为断言。

涉及真实集成、并发、事务或迁移等要求时，按当前任务补相应验证。内存仓库或模拟客户端的通过不能外推为真实数据库、网络协议、事务或迁移已验证；必要环境不可用时明确保留缺口。

用例独立准备并清理自己的数据、临时文件、连接和后台任务，失败时也应清理；不依赖执行顺序、其他用例留下的状态或开发者本机配置。用可控时钟、随机源和同步机制构造场景；随机探索失败保留种子及最小可复现输入。异步或并发验证使用事件、屏障或有超时的条件等待，不靠固定休眠碰运气。超时用于限制等待，不能未经约定就当作性能达标判据。

出现偶发失败先查共享状态、时间和资源竞争等原因，不能用无限重试、随意延长休眠、跳过用例或只保留成功的一次掩盖。运行器确有重试时如实保留首次失败和重试结果；环境问题与业务结果分开报告。

## RED → GREEN → 重构

1. **RED：** 新增或复用一个能证明目标行为缺失的测试，先运行，核对命令选中了目标用例及其失败位置。通常应由目标行为的断言失败；若待新增的公开模块／符号尚不存在而阻止用例执行，核实导入路径及其他依赖正确后，该缺失也可作为 RED，但不能据此声称行为断言已执行。测试自身语法错误、错误导入、环境未准备或无关依赖错误不能冒充有效 RED。先修正这些条件再判断。
2. **GREEN：** 在架构与复用检查后，用最小且有效的实现满足行为；先修实现而非改预期。运行同一目标用例，确认用例及其断言实际执行，通过来自行为实现，而非未收集、跳过、预期失败标记、过滤错误或替身绕过。不要一次写完整批功能再补测试，也不要把只针对单个样例硬编码的答案作为完成；补上能区分错误实现的下一用例。
3. **重构：** 测试通过后，按实际需要消除重复和改善责任表达。重构不改变已约定行为，测试代码也应保持可读、独立预期和故障定位能力；避免把准备、动作和断言藏进难以核对的通用助手。运行受影响测试与相关回归；没有必要调整时不强行重构。
4. **下一切片：** 核对任务范围、实际差异及用例区分能力，再选下一个未满足的验收行为。每个新行为重复循环，最终执行影响范围内的验证，并核对验收与实际执行用例之间的对应关系。

实际测试输出、工具执行顺序或项目已有 CI 记录可以承载证据，不要求为每次运行新建文档。需要交接时保留命令、输入版本／工作区状态、结果与限制；不能在完成后补写一段没有执行依据的 RED 记录。

## 检查用例能否发现错误

对新增或实质修改的用例，核对“违反这条契约时，哪一条断言会失败”。例如移除归属检查、反转边界条件、漏写状态或重复发送事件时，相应测试应能报错。先检查测试路径、数据和断言；区分能力仍有疑问或漏检后果较高时，可在隔离副本中做有针对性的临时故障注入或运行项目已有变异测试。确认是目标断言因目标错误而失败，不能把语法错误、启动失败或超时视为有效检出；结束后移除临时故障并复跑相关测试。对契约下行为等价的变异，不为使其失败而锁死实现细节。

这类检查不要求每个任务引入变异工具或固定分数，也不替代新行为的真实 RED。若错误实现仍通过，应补强数据、断言或测试层级，不能仅增加重复用例数量。

例如，**假定有效契约明确规定**：只有订单所有者可取消未支付订单；首次成功后保存取消状态并发布一次取消事件；重复取消返回既定结果且不重复发布；被拒绝时状态不变且不发布事件。可据此设计：

| 场景 | 关键断言 | 应能发现的错误 |
|---|---|---|
| 所有者取消自己的未支付订单，另有一笔无关订单 | 返回契约结果、重读得到取消状态、事件内容与数量正确、无关订单不变 | 只改响应未保存、取消错对象、漏发／错发事件 |
| 非所有者取消订单，同时保留正常获准的对照用例 | 具体拒绝结果、订单状态不变、无取消事件 | 漏做归属校验、全部拒绝、先写入再报错 |
| 所有者取消已支付订单 | 具体拒绝结果、状态不变、无取消事件 | 漏做状态校验 |
| 同一订单连续取消两次 | 两次结果符合契约、最终状态正确、整个过程中取消事件总数为一 | 重复发布；仅检查最后一次调用而漏掉累积副作用 |

该例不代表所有项目都采用这些取消规则。若任务还要求并发幂等或数据库事务，需额外在相应边界验证，不能由连续两次调用的结果推断。

## 不同任务

| 情况 | 处理 |
|---|---|
| 缺陷修复 | 先建立或运行能复现缺陷的回归测试，再改代码；保留真实触发条件，修复后验证原问题及相邻有效／无效场景，防止通过一律放行或一律拒绝取得绿色 |
| 纯重构 | 先确保相关行为有测试并获取基线；缺少时补特征测试，不人为制造失败；每步验证行为保持 |
| 已有目标失败用例 | 核实预期有效并运行，直接作为 RED，不重复造测试 |
| 目标已经通过 | 检查环境、边界和任务是否仍有真实缺口；没有则交付核实结论，不制造失败或无效实现 |
| 文档、样式、配置或静态资源 | 根据实际风险采用渲染、配置加载、构建、静态检查或人工验证；有行为变化时仍应先定义并执行适用判据 |
| 无法准备必要环境 | 继续可独立验证的部分，标记未执行和阻塞；编写了测试不等于执行通过 |

测试本身过时或错误时，依据有效需求修正并记录理由及影响。不得仅为适配当前实现而修改断言、跳过用例、降低标准或删除失败测试。临时实验和试错记录不等于最终通过证据。

## 切片完成前的质量核对

- 预期有可定位的有效依据，验收的相关正常、边界、拒绝和失败后果有对应用例或明确未验证项。
- 用例经过目标行为及必要边界，预期独立；能指出它应拦截的具体错误和对应断言，没有替身自证或只检查表面成功。
- 测试可独立执行、数据与资源隔离，异步断言被等待，偶发失败未被重试或跳过掩盖。
- 实际执行覆盖目标用例，RED 原因有效，GREEN 及相关回归对应当前实现；零用例、跳过、未执行、阻塞和旧证据没有混入通过结论。

质量缺口在当前切片内修正；确受条件限制时按[验证与交接](verification.md)说明具体未验证行为及影响，不以用例数或覆盖率达标代替完成判断。
