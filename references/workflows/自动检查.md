# 自动检查与流程接入

自动化执行可确定的检查并返回原始证据，审查者判断需求、设计和真实后果。本流程不限定语言、框架、包管理器或 CI 平台；优先调用目标项目已有脚本、任务入口和 CI。检查集合由项目必需项与本次改动的实际影响共同确定，不默认安装一套工具或运行所有类别。

## 1. 发现项目检查入口

先读取仓库指令、贡献说明、构建／依赖配置及既有 CI，确认命令实际做什么，再决定执行范围。文件名和工具名仅是线索，不能看到某种语言就直接套用默认命令。

| 项目形态／线索示例 | 需要查明的事实 |
|---|---|
| JavaScript／TypeScript：`package.json`、锁文件、工作区配置 | 项目使用的包管理器、实际 scripts、单次运行参数、包之间的依赖与根级检查 |
| Python：`pyproject.toml`、测试及任务配置 | 实际使用的环境与测试、静态检查入口，不默认采用某个测试框架 |
| Java／Kotlin、.NET、Go、Rust、C／C++ 等：构建文件、项目／工作区文件、包装脚本 | 工具链版本、构建目标、测试模块、条件编译与平台要求；优先已有包装器和任务 |
| 多语言、单仓多包或容器化项目 | 各模块入口、共享库与调用方、跨语言契约、CI 矩阵、实际运行目录和环境 |
| 文档、配置、基础设施或静态资源项目 | 已有解析、校验、链接、渲染、构建或计划检查，不强行为其增加单元测试框架 |

为选中的每项检查确定：用途和验收关联、命令与工作目录、输入范围、必要环境、是否会写文件或使用共享资源、超时和通过条件、是否必需。已有任务或几行执行说明即可，不强制创建配置。

区分同名命令的真实行为，例如 `test` 可能默认进入 watch，`lint` 可能自动修复，`build` 可能隐含下载、迁移或发布。使用有界、会退出的检查模式；环境准备与检查结果分开记录，不静默安装依赖、改锁文件或执行部署。CI 中依赖特定系统、服务或平台的必需项，本地无法等价运行时保持待验证。

## 2. 进行哪些自动化检查

先保留项目要求的必需项，再按下表补齐本次影响所需的检查。同一项目入口已覆盖多项时复用其结果，不重复运行。项目没有对应工具时，先用已有能力构造最小有效检查；确有必要才补脚本或用例，不为凑齐类别引入工具。无法自动判断的部分交给[代码审查](代码审查.md)或运行验收，不将其记为自动检查通过。

| 检查类别 | 自动检查的内容 | 何时选择／扩大范围 |
|---|---|---|
| 目标测试与相关回归 | 新行为、缺陷复现、正常与错误路径是否符合契约，受影响既有行为是否保持；确认目标用例实际被收集并执行 | 行为变更先验证目标用例，再沿依赖扩展回归；纯重构用既有行为基线，测试设计与 RED／GREEN 见 [TDD](tdd.md) |
| 格式、lint 与静态分析 | 格式规范、语法、可确定的错误模式及项目已配置的规则 | 修改相应源码、脚本或规则配置时执行；使用检查模式，自动修复后重新固定输入并验证 |
| 类型、编译与构建 | 类型／符号解析、接口使用、模块引用、编译链接，以及适用的打包／产物生成 | 涉及类型、公开接口、模块、依赖或构建配置时执行；单元测试未经过生产构建时补实际构建目标 |
| 架构与依赖边界 | 项目已有规则可判定的依赖方向、禁止导入、模块循环、可见性及生成文件一致性 | 新增模块、调整职责或跨层依赖、修改共享能力时选择；工具没有覆盖的架构判断仍需审查 |
| 接口、契约与兼容性 | API／事件／文件格式的 schema、序列化、错误映射，适用的生成客户端与消费者契约 | 修改对外接口、共享类型、协议或跨服务边界时执行；按实际兼容要求检查调用方，不只测提供方 |
| 集成、数据与迁移 | 真实适配器、存储读写、约束、事务和项目要求的迁移加载／升级路径 | 修改数据库、消息、缓存或外部适配器时选择相关集成；迁移在可丢弃环境或项目认可的验证环境运行，替身通过不能代替真实边界 |
| 界面、交互与端到端 | 组件行为、路由、关键用户流程及受影响的布局、视觉基线或可访问性规则 | 改动 UI 或前后端接线时按影响选择；组件测试不证明完整流程可用，自动截图仍需按验收核对实际结果 |
| 配置、文档与静态资源 | 配置解析／schema、链接与引用、模板／文档渲染、资源引用及相关构建 | 修改对应文件时执行；文档中的可执行示例按需要验证，不因不是源码就默认没有检查 |
| 依赖、安全与基础设施 | 锁文件／清单一致性、项目已有漏洞／凭据／安全规则、基础设施语法与适用的计划检查 | 依赖、授权、敏感数据处理、部署或基础设施变更涉及这些风险，或项目已有必需扫描时执行；不自动扩展为全仓审计或实际应用计划 |
| 性能与资源 | 有约定的性能预算、泄漏或资源上限；使用项目已有基准和可重复条件 | 本次有相关验收或具体回归风险时执行，记录环境与测量条件；普通测试超时不能证明性能达标 |

用影响范围选择组合，而不是只按文件扩展名选择。典型组合如下，均须加上项目另行要求的必需项：

- **业务规则或缺陷修复：** 目标测试＋受影响回归＋适用静态／类型检查；若涉及持久化或外部调用，再加入相应集成。
- **共享库或公开接口：** 提供方测试＋契约／兼容性检查＋受影响调用方测试／构建；不能只跑修改包自身的单测。
- **前端组件或页面：** 相关组件／交互测试＋适用 lint／类型检查＋受影响构建；涉及跨端流程或视觉要求时加入端到端或视觉检查。
- **数据迁移或构建配置：** 迁移／配置校验＋真实升级或构建路径＋受影响集成；CI 矩阵或平台差异保留在相应环境验证。
- **仅文档或资源：** 对应链接、解析、渲染或资源构建；无需无依据地执行与改动无关的业务测试。

单仓多包先验证修改模块，再沿共享依赖、生成输入和跨模块调用扩大。使用项目已有的“受影响目标”机制前，确认基线和依赖图能覆盖本次差异；锁文件、根配置、共享协议或生成器变化可能要求跨包检查。项目规定的全量回归、构建目标或 CI 矩阵不能被局部通过替代。

## 3. 选择触发时点并执行

| 时点 | 执行内容 | 判断边界 |
|---|---|---|
| 实现前 | 相关测试或其他适用检查的基线 | 原有失败记录来源和影响，不当作新实现的 RED |
| 切片或相关文件变化后 | 目标测试、受影响回归及上节选中的检查 | 快速反馈先聚焦，沿真实影响扩大；未运行的必需项仍待验证 |
| 独立审查前 | 本轮适用的必需检查集合，保留证据 | 失败先定位，与失败无依赖的审查仍可进行 |
| 修复后 | 缺陷复现用例及受影响检查 | 修改测试、配置或调用边界时一并重验；不重复整个无变化过程 |
| 交付、提交或已有 PR 更新时 | 核对证据有效性，补齐已有 CI 必需项 | 待运行、失败、超时和旧提交结果不能冒充当前成功 |
| 已授权的合并或发布 | 项目要求的合并后检查、冒烟及恢复核对 | 沿用项目实际流程，不从普通编码自动进入发布 |

自动格式化、代码生成等会改写受验输入的步骤先完成，再固定本轮检查输入。检查期间有相关写入时，重新核对差异和受影响结果；不能把修改前后的不同状态拼成一轮整体通过。

检查命令在已确认的任务路径运行，核实其输入版本、运行环境和副作用。

本地回合并属于[默认交付](回合并.md)，核实最新目标的实际整合候选，并将合并后必需检查关联到目标最终提交。远端 PR 自动合并、推送与发布不因此获得授权。

## 4. 判断结果与处置失败

命令退出码是必要证据，还要核实它检查了预定对象。零用例、目标用例全被跳过、错误筛选、旧产物或缓存命中但输入关联不明时，不能据此证明目标行为通过；确认项目工具的实际语义后再下结论。

| 结果 | 处置 |
|---|---|
| 通过 | 记录实际覆盖范围与输入状态；仅在该范围内复用，不外推为整体验收或审查通过 |
| 测试断言或规则失败 | 结合基线定位本次引入、原有问题或规则／预期错误，依据有效要求修复并复验；不能为消除失败随意改预期 |
| 命令不可执行、依赖／服务缺失、超时或被取消 | 标为未完成或执行受阻，说明缺少条件和必要的补验；不记为业务检查通过 |
| 偶发失败 | 保留首次失败与实际重试结果，排查环境和共享状态；不只保留成功一次或无限重试 |
| 不适用或项目允许的建议项失败 | 说明不适用依据或建议项影响；必需项不能因运行失败、耗时或环境不可用而静默降级 |
| 输入、配置或关键环境已变化 | 标记相关旧结果需复核，按影响重跑；无法判定影响时保留缺口 |

## 5. 保存证据与接入自动化

直接运行项目命令、沿用既有 CI 或使用可选执行器都可以。证据至少能定位命令及工作目录、提交或工作区输入状态、必要环境、起止时间、退出码和原始日志，并说明实际覆盖、失败及未执行项。工具链／依赖版本、运行平台或外部服务影响结论时一并记录；不把凭据写入日志或报告。小任务可复用现有输出，不要求统一 JSON 或专门平台。

交付前核对受验代码、测试、规则、依赖锁文件及相关配置是否仍匹配；环境或外部系统变化也可能使旧结论失效。本地证据对应最终工作区，CI 证据对应实际提交及适用矩阵；不同运行范围的通过不能相互冒充。

宿主已有文件事件、任务结束事件或 CI 入口时，可接入同一检查命令。是否阻止完成取决于宿主／CI 如何处理退出码，Markdown 本身没有强制能力。结束事件只核实当前结果，过期时返回原因并安排修复／重跑；使用宿主真实协议及防重入机制，避免反复启动审查或无限重试。未实际安装和验证时，只说明配置方法，不声称自动触发已生效。

CI 优先沿用已有检查和工件上传机制，即使失败也保存日志；关联实际提交，不默认推送代码、发布评论、放宽必需检查或配置远端 PR 自动合并。最终按[验证与交接](verification.md)分别报告自动检查、独立审查、运行验收及规定的人审结果。

需要批量运行、统一日志或核实旧证据时，再读取[可选执行器用法](自动检查执行器.md)。包内执行器使用 Python 标准库实现，可调用不同技术栈的命令；仅选择该工具时需要 Python，不要求目标项目采用 Python，也不要求为运行工作流而安装它。
