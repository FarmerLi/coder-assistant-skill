# 验证、交付与反馈

## 验证范围

先验证当前切片，再按真实依赖与副作用扩展到相关模块、接口、调用方和数据。运行项目要求的必要检查；选择类型、静态检查、构建、架构、契约、集成、回归或渲染等适用项，不默认运行所有工具，也不遗漏项目必需检查。

检查成功后，只有新修改、失败或未解决风险才扩大或重复验证。原有失败与本次引入问题分开处理；证据不足时说明尚无法判断，不能仅因名称无关就排除影响。

## 分层验证与整合

确定性检查按[自动检查](自动检查.md)复用项目本地／CI 入口，独立判断和缺陷处置按[代码审查](代码审查.md)执行。实质行为变更或复杂改动优先由[独立验证子代理](../agents/独立验证.md)在新的上下文检查；小且低影响的改动或宿主不支持委派时，主 agent 完成相应检查并如实说明独立性限制。委派和修改归属按[子代理协作](../shared/子代理协作.md)执行。

自动检查、代码审查、运行验收及项目规定的人审分别关联实际结果，某一面通过不能代替其他必需项。主 agent 核对发现与实际文件，对每项实质问题修复并复验或给出有证据的处置理由；已修改但未复验的项保持待验证。

独立切片各自通过后，主 agent 仍须检查整合后的接口、共享状态和必要回归。证据附其适用的实现状态；验证后有相关修改时标明受影响结果需复核，不能把各子任务的通过直接相加为整体通过。

按[并发工作区](../shared/并发工作区.md)核对受测路径及版本，包括应用实际运行的代码。并发开发不要求并发启动完整环境；重型集成可在整合后集中执行，必需项在实际运行前保持待验证。

## 交付前核对

- **范围：** 从本次开始的工作区基线查看自己的改动及新增文件，逐项对应有效任务、验收或必要支撑；移除自己的无关扩展，保留他人修改。
- **架构：** 检查实际责任、依赖、数据访问、接口兼容和必要迁移，保留自动检查或具体人工证据。没有报错不等于所有边界都已覆盖。
- **复用：** 回查新增逻辑是否重复已有能力，重要新建和抽象是否有理由；按真实语义处理，避免机械合并。
- **验收：** 将验收行为关联实际用例与执行结果，区分已定义、已实现、已执行、通过和需复核。局部测试通过不能代替全部范围。
- **证据：** 确认运行针对当前输入及实现状态，记录版本或可定位工作区状态、环境、结果与限制；未执行明确说明。
- **发现处置：** 已确认问题有修复复验或有效处置理由；误报与有意行为有依据，未解决项和影响明确。必要检查没有被降级、忽略或借用其他提交的成功结果。

不要只写“符合架构”“测试通过”“复用完成”。证据可以是已有检查结果和几行定位说明，不要求为每项建立新表格。

## 完成判断

当前任务范围的行为已实现，适用架构与兼容约束满足，必要检查和验收有相应证据，阻塞与遗留按约定处理，才能报告该范围完成。只完成部分时明确部分范围，不把已写测试、替身通过、任务关闭或代码已提交当成完整交付。

任务没有要求部署或业务验收时，不自行增加上线关卡；确有这些要求则分别关联实际结果。不能证明整体完成时，交付已有成果并说明下一步，不夸大也不隐藏。

## 结果与交接

回复以结果为先，简要说明做了什么、为什么如此实现、如何验证、还有哪些限制。重要复用选择与架构检查给出具体位置。无需重复完整执行过程。

需要恢复时依[上下文约定](../shared/project-context.md)更新现有记录，或使用[模板](../../assets/开发交接模板.md)。包含有效输入、范围、当前改动、最后真实测试、发现处置、未决问题和下一步；保留检查及审查对应的代码状态，不让进度摘要替代需求正文。重复失误按审查方法反馈到回归、确定性规则或适当约定，不默认建立监控或遥测。

需要同步远端时先读取当前内容和关联，按授权保留无关信息；超时或结果不明先查询，避免重复创建。仅关闭任务或更新状态不发送额外评论、消息或通知，除非已有明确授权。
