# 代码复用与重复控制

## 先定位已有能力

编码前从需求语义、入口、相邻模块、调用方和测试搜索已有能力。优先查看公开服务、领域规则、错误处理、验证器、数据访问和测试工具，再按实际缺口扩展搜索；找到足够依据即可停止，不以搜索次数衡量充分性。

判断候选是否可用，需要核对：业务语义、输入输出与错误契约、权限及副作用、状态和事务、性能与兼容、合法依赖方向。名称和代码形状相似都不足以证明等价。测试夹具也不能替代生产能力。

## 做出适当选择

| 选择 | 判断依据 |
|---|---|
| 直接复用 | 已有公开能力满足当前行为和约束 |
| 扩展 | 只缺少相关行为，可保持既有调用方与责任清晰 |
| 组合或适配 | 已有能力可协作承载需求，需要合适的边界转换 |
| 提取共享能力 | 存在真实重复、共同语义及具体调用方，提取后依赖和变化责任仍合理 |
| 新建实现 | 没有合适能力，或复用会破坏语义、职责、依赖及其他明确要求 |

重要选择保留几行依据：候选位置、契约差异、采用方式及测试影响。简单调用无需另建报告；新模块、新依赖或公共抽象应能说明现有能力为何不足。

不要为了“以后可能复用”创建通用平台、插件系统或万能工具类。不同业务的相似逻辑可以保留独立实现；不能用大量配置开关掩盖语义差异。不设统一复用率或重复行数通过线。

## 在测试保护下调整

复用前读相关测试并补缺失行为。扩展或提取时检查已有调用方、错误及副作用，必要时补回归；共用测试工具仍须保留用例自己的业务预期，避免测试直接调用与实现相同的算法计算答案。

切片结束与交付前，针对新增逻辑及相关模块检查重复：是否新增了第二套规则、状态机、校验或数据访问？是否存在仅名称不同的同义实现？优先合并实际发现的问题，保留不同语义；不将局部检查扩大为全仓清理。

已有重复超出本次影响时记录位置和建议，不能以“提高复用”为由无边界重构。
