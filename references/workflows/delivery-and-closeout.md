# 提交、整合与收尾

## 先选择交付路径

开始时先读取用户要求和项目接入参数，确定目标、交付边界、验收来源与已有授权。默认开发交付边界为实现、验证及约定提交／PR，完成后进入待反馈状态。父任务的内部整合按下节执行；主线合并和收尾须有相应授权。明确的提交后等待约定优先于默认收尾设置；已有有效收尾授权且无等待限制的，连续完成已授权操作，不重复索取许可。项目提供交付模式、主线目标、分支／提交格式、平台字段和检查名、合并方式、运行资源及实际工具入口；这些是本流程的参数，不在项目另建调度、审批或收尾正文。用户明确例外优先；配置仅选择已采用的模式，不代表本轮操作授权。

| 适用约定 | 执行路径 |
|---|---|
| 只交补丁、不提交／不合并或仅创建 PR | 完成约定结果及验证，到明确边界结束 |
| 项目采用 PR 交付 | 完成本轮提交、推送及创建／更新 PR 后报告并等待；本地回合并不能替代远端门槛 |
| 没有其他约定的 Git 编码任务 | 在任务分支本地提交后报告并等待，不自动更新目标分支或推送 |
| 本轮明确包含合并及收尾 | 按 PR 或本地路径完成已授权收尾，仍须满足全部门槛 |
| 非 Git 项目 | 沿用文件交付约定，不强行初始化 Git |

## PR 交付路径

1. 记录任务工作区、分支、目标分支、基线及依赖，保留既有修改。父任务采用下节集成分支模型；同一未合并 PR 的修复沿用原分支／PR，子 PR 已合入父集成分支而主项尚未交付时，可沿原子 Issue 建补充修复 PR；主线已交付后的新增任务按项目规则另建。
2. 按已有授权提交并推送本次改动，创建或更新 PR。临时任务说明目标；需求任务关联定位与行为摘要；说明主要实现入口、方式、实际验证和未验证影响。PR 格式使用项目模板，阶段判据见下节。
3. 完成本轮交付所需的自查、独立验证和适用检查，核实并修复问题，保留对应提交的证据。子项按自身验收范围交付，不逐个等待主项全量 CI；远端排队／运行中与主项整体验收待办分别报告。达到约定交付边界后，按[等待与反馈规则](#提交后的等待与评审反馈)进入待反馈状态；父任务内部的子 PR 按下节继续整合。人审若为必需项，须有真实接受记录，不由 agent 自评代替；作者与审批者身份及平台限制须核实。修改后依据影响及平台规则复核旧证据，不能把旧验收无条件移到新提交。
4. 仅在本轮包含合并收尾时，按项目规定验证与最新目标组合后的候选，复用既有 CI／队列；检查通过不等于已合并。获准自动合并时使用平台机制并保留所有门槛，已有验收与授权不重复索取；未授权或条件缺失时只暂停依赖动作，不本地绕过、不放宽检查。
5. 获授权且实际合并后查询 PR 状态和目标提交，按项目要求执行同步、环境准备、关联Issue关闭及清理，关闭条件见末节。Squash 等方式改变提交关系时，通过合并记录与实际结果核实，不仅比较任务提交祖先关系。共享或已推送提交不得未经授权 rebase／强推；目标变化按项目认可的更新方式处理。

PR／检查调用超时先查询再重试。验收失败、无法确定冲突解法、权限不足或执行器不可用时保留成果，说明当前阶段和恢复入口。持续跟进须有实际运行的执行器或自动化；不能仅凭指令承诺对话结束后仍在监听。自动重试须有项目规定的次数／时间边界，反复相同失败时停止该动作并报告，不无限重跑或改变验收标准。

本地同步前确认目标工作区仍为约定分支、干净、无需要稳定版本的调试或其他写入占用且可安全快进。普通终端、编辑器、其他工作区或允许热更新的应用存在，不单独阻止同步。否则记录待同步，保留现场，待条件恢复由执行机制继续；不自动 stash、reset 或强切分支。环境准备沿已有入口，失败独立记录，不冒充同步及交付全部完成。只在成果可恢复、无未交付修改且本任务进程停止后回收任务资源；取消也不能直接删除未保存工作。

## PR 阶段与人工验收

| 阶段 | 可检查条件 |
|---|---|
| Draft | 已有可审查增量，尚未满足本项交付检查；明确缺口与依赖 |
| 待评审／待验收 | 本轮实现和适用本地检查完成，目标及验证证据可定位，说明远端检查及人工验收实际状态 |
| 子 PR 可集成 | 自身 AC、直接影响、独立评审和当前父分支组合所需检查满足；平台必需检查仍须通过 |
| 主 PR／独立主线 PR 可合并 | 完整范围及当前目标组合验证通过，要求的人审与平台门槛满足，且已有本轮合并授权 |

项目采用主线人工验收模式时，主 PR 及直接交付主线的 PR 都须有实际接受记录；子 PR 仍按自身判据，不默认追加主线人工／全量关卡。人工接受记录关联 PR、完整 head SHA、验收范围、结果及可追查来源，与合并授权分别核实。查看页面、启动服务、测试成功、提交 review 或 AI 独立审查均不单独等于接受。作者不能用同一账号绕过平台自我批准限制。

页面／接口任务交付时，在会话提供实际受测版本对应的完整访问地址及必要使用方式；人工验收进行期间保留所需服务，无法提供时说明缺口。截图仅在有验证用途时提供，不能替代实际访问。文档任务验收正文，不强制启动无关应用。

新提交后核对受影响检查与人工接受范围。不影响原验收内容的变化可保留差异比较和沿用依据；行为、范围、关键取舍或冲突解决改变验收对象时重新验收受影响部分，不能把旧接受自动绑定到新 SHA。无法判断时保持待验收。

合并前核实最新目标及实际候选。有合适 Merge Queue 时使用其候选检查，否则安全更新目标组合后验证；不得凭旧 base 的绿色结果合并。平台不支持保护时，可使用已获授权的受控执行器核对同等证据，并以 head 条件调用正常合并接口；必须披露其不能约束其他写入者或完全消除检查与合并间竞态，不能将本地约定声称为平台强制保障。平台已有保护和必需检查不可绕过。

## 父Issue集成分支与子PR

包含多个可独立交付子项的父 Issue 使用父集成分支及权威工作区，基线为项目指定目标的最新有效提交。子项各有独立分支／工作区，默认从父集成分支启动，子 PR 的最终集成目标也是父分支；完整父目标通过主 PR 交付到项目主线。简单独立 Issue 继续采用直接 PR，不为形式增加父分支。分支命名沿项目约定，跨仓库各有对应集成分支／主 PR 并关联共同验收，不声称跨仓库原子合并。

父任务的实施授权包括约定子项开发、子 PR、独立验证及向父分支的内部整合；明确的授权限制优先。子 PR 由集成负责人核对自身 AC、直接影响、独立评审及当前候选所需检查，记录 head、目标基线、受测候选和结果后，通过正常平台 PR 机制合入父分支；不默认逐项追加业务人工验收或主线全量关卡，子项明确要求人工判定的结果除外。内部整合不等于合入主线，也不自动授权最终主 PR 合并。

父 agent 统一协调父分支写入与子 PR 整合，不在子工作区同时写入。无依赖子项并发；代码依赖未合入父分支时按下节暂基于前置子 PR 开发，前置合入后安全调整到父分支、检查本项增量及相关回归。父分支因其他子项或主线更新而变化时，复核直接影响的接口与证据，不为每次内部整合重复跑完整系统验收。

首批代表性子项形成后先执行[跨项风险检查](verification.md#跨项风险前置)，不等待最终全量才发现公共边界问题。本轮必要子项整合后，从父分支建立面向主线的主 PR，核对完整父范围及遗漏，在对应稳定整合候选上统一组织跨项与约定全量验收，再交用户 review／人工验收；可按项目约定提前开 Draft，但不因此提前宣称全部就绪。尚未完成的全量、远端 CI 和人工验收分别报告。最终主 PR 合并须另有本轮收尾授权及全部主线门槛，完成后才称主目标已交付。

子项关闭以自身结果、独立验证及合入父分支等约定条件判断，主线发布并非所有子项的隐含前提；记录父分支／主 PR 及所用提交，不能把子项关闭当成产品已上线。主项验收发现子项缺口时由原子 Issue 承接修复或重开，并向父分支提交补充 PR，不能以子项已关闭免除修复。非默认目标分支的自动关闭关联是否生效须核实；保留仍被下游依赖或承载未交付成果的分支与工作区，最终交付前不提前清理。

## 依赖PR上的分支开发

是否可启动按[依赖调度](../shared/execution-contract.md#父issue执行与依赖调度)判断；这里处理 Git 与 PR 边界：

1. 核实前置 PR 的实际分支、head 提交、所需产物及相关检查。把该确定提交作为下游分支／独立工作区的起点，记录前置 PR、已消费的提交和下游范围；不复用前置工作区，不改写其历史或代其验收。
2. 同仓且平台支持时，下游 PR 的 base 暂指向前置 PR 分支，让评审差异只展示本项增量；正文关联依赖并说明临时 base、基线和后续调整条件。继承前置提交不代表本 PR 实现了前置 Issue，不重复申领成果或提前关闭它。跨仓库或多个前置按项目支持的集成方式核实实际组合，不伪造可以直接堆叠的分支关系。
3. 前置 PR 新增提交或改契约时，核实本项需要跟随的变化，通过项目允许的安全更新方式同步并重验受影响项。共享／已推送历史不因堆叠而获得 rebase／强推授权。前置被拒绝、取消或不再提供依赖产物时，仅暂停受影响部分，保留分支成果并重核依赖。
4. 前置合并后，核实其实际目标提交，再按项目规则将下游 PR 转向最终目标，安全消除重复前置差异；Squash 后不能只凭祖先关系判断。核对本项增量、当前 head/base 与组合检查，不能直接沿用临时 base 的通过结果。采用父集成分支时，本节的最终目标是父分支；其主 PR 才面向主线。各 PR 仍按各自验收和合并条件交付，清理前保留仍被下游引用的分支与成果。

## 提交后的等待与评审反馈

父任务的本轮交付包含已约定的子 PR 内部整合及最终主 PR，不能在每个子 PR 提交时单独停止整个父任务。本轮授权且可推进的范围完成约定实现、验证及提交／PR 后，报告成果、提交／PR、实际检查和待评审／阻塞状态，然后结束本轮等待用户下一步指令。父 Issue 内其他可推进项继续执行，不能把单个子项待 review 当作整轮停止条件。测试通过、PR 可评审或创建成功不构成主线合并授权；子 PR 内部整合遵循前述门槛，不关闭未完成 Issue，不清理仍需返修或被下游依赖的现场；不轮询未来 review、不创建后台监听或定时任务。

评审反馈处理以已提交评审通知或明确的处理指令为入口，沿原任务和 PR 读取实际 review、行内评论、对应提交及当前差异，并直接核实、处理原任务范围内的问题，不增加启动确认。Submit review 是评审提交动作，不代表批准或人工验收通过；Pending、Comment、Request changes、Approve 按平台实际状态与内容分别判断，平台审批不自动替代项目规定的业务验收。

逐项核实评论与有效需求：确认的缺陷在原任务范围内修复：未合并 PR 沿原分支处理，已合入父分支的子 PR 按前述规则建立补充修复 PR，补充适用测试并复验；有证据的误报或已过时评论说明依据；会实质扩大目标或改变验收的建议只就变化项取得决定，不自行接受新范围。新提交后复核受影响审查、人工验收和 CI 证据；若修复改变前置契约，同步核对依赖它的下游。完成本轮约定修复和 PR 更新后，再报告并等待；不因收到评论而自动获得合并授权。

评论读取、代码修复和在远端代用户回复／提交 review 是不同操作，后者仍须有明确发送授权。工具无法读取评论时说明实际缺口，请用户提供评论内容，保留其余已完成成果，不臆造 review 结论。

## 本地回合并路径

仅在本轮明确要求本地回合并时适用；本地提交后等待的默认路径不执行本节。由主 agent 按“本地提交 → rebase 到最新目标 → 验证 → 目标快进更新”交付，同时更新主仓库目标分支及工作区。使用 Git 提交级整合，不复制文件覆盖主仓库，也不默认创建 merge commit。无需逐次询问是否提交或回合并；用户明确只要补丁、不提交、不合并或项目有明确交付流程时沿用其要求。本地回合并不包含自动推送、远端 PR 合并、部署或发布。

## 开始时定位目标

记录目标仓库、原始工作区绝对路径、目标分支及起始提交。优先沿用用户或项目明确的目标；没有另行指定时，使用启动任务的原始工作区当时所在的本地分支，不猜测固定名为 main 或 master，也不把远端地址当成本地目标。目标处于 detached HEAD 或存在多个有效目标时，先查已有任务与交接；仍无法确定则只暂停回合并，继续不依赖该选择的开发。

入口已是任务专属 worktree 时，从宿主创建来源或已有交接定位原主工作区及目标分支，沿用已记录目标，不能把任务分支自身当作回合并目标。任务跨会话续做不改变回合并目标，也不因此新建 worktree。缺少来源时先核实仓库 worktree 信息，仍不能确认则报告具体缺口。

记录任务 worktree、任务起始输入与带入的已有修改。只提交本次任务改动，使用明确文件或选定差异暂存，不把用户已有修改、他人工作、缓存和验证工件顺手提交。本次实现若依赖尚未提交且无法分离的已有修改，说明具体依赖并保留结果，不能代用户提交这些内容。

## 整合并更新主工作区

回合并由任务主 agent 执行，先核实本任务相关子任务已结束，待提交差异完整且相关输入保持稳定。

1. **核实目标与前置状态。** 重新确认目标工作区仍检出记录的目标分支、没有进行中的合并／变基及未提交修改，包括暂存和未跟踪文件；确认任务提交及其验证证据有效。目标不干净时保留其状态，不自动 stash、提交或清理用户工作，标明回合并暂未完成。
2. **Rebase 到最新目标。** 读取当前目标提交；先核实已记录的任务结果（含 rebase 后提交）是否已被目标包含，已包含时核实目标状态与所需验证，直接报告已合并。否则确认待重放序列只包含本任务尚未共享的提交，在任务 worktree 执行 `git rebase --no-autostash <目标最新提交>`。不重放、改写其他任务或已回合并的提交，不强制回退目标；不能确认提交归属时保留结果并报告具体缺口。
3. **验证 rebase 后候选。** 在任务 worktree 处理有明确依据的 rebase 冲突，保存重放前后提交对应关系，按[整合复审触发条件](code-review.md#整合复审触发条件)检查实际差异、接口与受影响回归，完成必要的独立复审和集成验证。无法确定正确解法或检查失败时保留任务结果，目标不动，明确报告未合并。复用证据须核实其对当前候选仍有效，不能直接借用 rebase 前通过。
4. **快进更新目标。** 再次核实目标分支、提交及干净状态，使用普通 Git 安全更新，例如在目标工作区执行 `git merge --ff-only --no-autostash <已验证候选提交>`。目标在检查期间又变化时回到最新目标重新整合并验证，不能强制更新引用、reset 或覆盖文件；持续变化时保留结果并报告暂未合并。
5. **核实完成。** 确认目标分支和工作区实际包含本次结果，在目标状态执行项目要求的合并后检查，记录最终提交、受测状态和结果。合并后检查失败时如实报告“已合并、验证失败”，保留现场并修复，不自动重置目标。

任务在 detached worktree 开发也可使用已保存的候选提交；目标必须是已定位的本地分支与工作区。不能绕过 Git 对其他 worktree、未提交修改或分支状态的保护。

## 本地路径完成判断与恢复

本轮明确要求本地回合并时，完成条件同时包含实现验收和回合并；默认提交后等待时，以约定提交及交付证据判断本轮完成，并保留未合并事实。仅 worktree 测试通过、仅生成补丁或仅创建本地提交时，分别报告实际进度，不能称已合并回主仓库。非 Git 项目按已有文件交付约定处理，不强行初始化 Git 或伪造合并结果。

Rebase 完成后、更新目标之前即保存原任务提交与 rebase 后提交的对应关系。恢复时先核实原目标、该对应关系、目标当前 HEAD、是否已有 rebase 进行中及是否已包含重放后的结果，再继续；不能仅因原提交哈希改变而重复交付。调用超时或中断不能直接重复提交、rebase、快进或删除 worktree。记录“未合并／已合并待检查／已合并且检查通过”等实际状态。确认目标包含结果、必要检查通过、证据已保留且执行者停止后，才按宿主约定回收本任务的临时 worktree；受阻时保留它。

## 资源回收

本地主线同步、环境准备、任务资源回收分别判断；主线有草稿或分叉不能同步时，不阻断满足条件的本任务清理。停止应用、归档工作区、删除分支和清理数据分别记录；没有明确数据清理范围时保留数据。验证服务按[资源预算](automated-checks.md#验证资源与执行预算)及时停止，不必等主线合并才释放临时进程。

宿主管理的 worktree 使用原生归档入口，核实成果与必要忽略文件可恢复、没有未交付修改、写入和调试已结束。当前聊天、固定或共享工作区被宿主保护时，记录“已完成，工作区因平台限制保留”及路径／分支；不以 shell 强删绕过，不反复留下没有可执行动作的待办。手工创建的 worktree 才按显式 Git 清理方式处理。保留不写成删除，归档不代替 Issue 完成。

## 关联Issue关闭与现场清理

项目或用户要求Issue收尾时，沿已有任务授权及[Issue用途](../shared/execution-contract.md#issue用途与执行入口)执行。反馈因重复、拒绝或转讨论处理时记录对应决定及关联，不能写成实现完成，也不要求补齐执行AC后才能分诊收尾。

执行Issue不因代码已提交、单个子任务完成或工作区可清理就关闭。先核对完整验收要求、必需检查和交付边界；本项明确需要人审时核实实际接受记录，需要 PR 交付时核实其已合入约定目标；不把存在 PR 自动等同于需要业务人工验收；子项合入父集成分支可以满足自身交付条件，不能据此关闭仍待全量验收／主线交付的父项。仅交补丁的明确任务按其约定验收，不擅自增加合并义务。多PR／跨仓库任务以Issue完整范围判断，不能提前关闭父Issue。父项还须核对总体验收、必要子项交付及跨子项验证；所有子项已关闭只说明平台状态，取消／延期不能当作目标通过。

保留Issue与PR／提交、验收及测试证据的关联，然后执行关闭并按[状态同步](task-progress.md#按事件同步)回读 Issue 与相关看板实际状态；已自动关闭时仍核实完成条件。仅当合并本身满足所有关闭条件时使用自动关闭关联，否则用普通链接并在条件齐备后关闭。核实项目的父子级联关闭配置，不能用自动状态替代父项总体或子项验收；出现提前关闭时如实报告缺口，沿已有授权纠正状态。取消／放弃须有明确决定并采用对应原因，不写成实现完成。

未完成条目、失败检查或待验收仍存在时保持打开。关闭调用超时／中断先查询再重试；权限或工具不可用时记录待关闭和恢复入口，不声称关闭成功。Issue关闭、本地同步、环境准备及资源清理分别记录；清理因宿主限制受阻不自动否定已完成验收，但Issue明确包含清理验收时须完成该项。清理前确保成果与证据可恢复，关闭不隐含删除数据或发送额外消息／评论的授权。
