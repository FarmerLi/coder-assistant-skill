# 提交、整合与收尾

## 先选择交付路径

开始时先读取用户要求和仓库协作政策，确定目标、交付边界、验收来源与已有授权。默认边界为本轮实现、验证及约定提交／PR 后等待用户下一步指令，不把实现任务自动延伸到合并收尾。用户明确要求提交后等待时，优先于项目默认自动合并约定；已有明确收尾授权且未要求等待时按约定连续完成，不再重复索取许可。项目的分支名、提交格式、平台检查、合并方式和资源并发规则由项目维护，本技能不另定一套。

| 适用约定 | 执行路径 |
|---|---|
| 只交补丁、不提交／不合并或仅创建 PR | 完成约定结果及验证，到明确边界结束 |
| 项目采用 PR 交付 | 完成本轮提交、推送及创建／更新 PR 后报告并等待；本地回合并不能替代远端门槛 |
| 没有其他约定的 Git 编码任务 | 在任务分支本地提交后报告并等待，不自动更新目标分支或推送 |
| 本轮明确包含合并及收尾 | 按 PR 或本地路径完成已授权收尾，仍须满足全部门槛 |
| 非 Git 项目 | 沿用文件交付约定，不强行初始化 Git |

## PR 交付路径

1. 记录任务工作区、分支、目标分支、基线及依赖，保留既有修改；同一未合并任务的修复沿用原 PR，已合并后的新修改按项目规则另建任务。
2. 按已有授权提交并推送本次改动，创建或更新 PR。临时任务说明目标；需求任务关联定位与行为摘要；说明主要实现入口、方式、实际验证和未验证影响。Draft、待评审、可合并的门槛及格式由项目规定。
3. 完成本轮交付所需的自查、独立验证和适用检查，核实并修复问题，保留对应提交的证据。提交后按下节报告并等待；收到评审后按其实际内容恢复。人审若为必需项，须有真实接受记录，不由 agent 自评代替；作者与审批者身份及平台限制须核实。修改后依据影响及平台规则复核旧证据，不能把旧验收无条件移到新提交。
4. 仅在本轮包含合并收尾时，按项目规定验证与最新目标组合后的候选，复用既有 CI／队列；检查通过不等于已合并。获准自动合并时使用平台机制并保留所有门槛，已有验收与授权不重复索取；未授权或条件缺失时只暂停依赖动作，不本地绕过、不放宽检查。
5. 获授权且实际合并后查询 PR 状态和目标提交，按项目要求执行同步、环境准备、关联Issue关闭及清理，关闭条件见末节。Squash 等方式改变提交关系时，通过合并记录与实际结果核实，不仅比较任务提交祖先关系。共享或已推送提交不得未经授权 rebase／强推；目标变化按项目认可的更新方式处理。

PR／检查调用超时先查询再重试。验收失败、无法确定冲突解法、权限不足或执行器不可用时保留成果，说明当前阶段和恢复入口。持续跟进须有实际运行的执行器或自动化；不能仅凭指令承诺对话结束后仍在监听。自动重试须有项目规定的次数／时间边界，反复相同失败时停止该动作并报告，不无限重跑或改变验收标准。

本地同步前确认目标工作区仍为约定分支、干净、无调试／其他写入占用且可安全快进。否则记录待同步，保留现场，待条件恢复由执行机制继续；不自动 stash、reset 或强切分支。环境准备沿已有入口，失败独立记录，不冒充同步及交付全部完成。只在成果可恢复、无未交付修改且本任务进程停止后回收任务资源；取消也不能直接删除未保存工作。

## 依赖PR上的分支开发

是否可启动按[依赖调度](../shared/execution-contract.md#父issue执行与依赖调度)判断；这里处理 Git 与 PR 边界：

1. 核实前置 PR 的实际分支、head 提交、所需产物及相关检查。把该确定提交作为下游分支／独立工作区的起点，记录前置 PR、已消费的提交和下游范围；不复用前置工作区，不改写其历史或代其验收。
2. 同仓且平台支持时，下游 PR 的 base 暂指向前置 PR 分支，让评审差异只展示本项增量；正文关联依赖并说明临时 base、基线和后续调整条件。继承前置提交不代表本 PR 实现了前置 Issue，不重复申领成果或提前关闭它。跨仓库或多个前置按项目支持的集成方式核实实际组合，不伪造可以直接堆叠的分支关系。
3. 前置 PR 新增提交或改契约时，核实本项需要跟随的变化，通过项目允许的安全更新方式同步并重验受影响项。共享／已推送历史不因堆叠而获得 rebase／强推授权。前置被拒绝、取消或不再提供依赖产物时，仅暂停受影响部分，保留分支成果并重核依赖。
4. 前置合并后，核实其实际目标提交，再按项目规则将下游 PR 转向最终目标，安全消除重复前置差异；Squash 后不能只凭祖先关系判断。核对本项增量、当前 head/base 与组合检查，不能直接沿用临时 base 的通过结果。各 PR 仍按各自验收和合并条件交付，清理前保留仍被下游引用的分支与成果。

## 提交后的等待与评审反馈

本轮授权且可推进的范围完成约定实现、验证及提交／PR 后，报告成果、提交／PR、实际检查和待评审／阻塞状态，然后结束本轮等待用户下一步指令。父 Issue 内其他可推进项继续执行，不能把单个子项待 review 当作整轮停止条件。不因测试通过、PR 已可评审或创建成功而自行合并、关闭未完成 Issue、清理仍需返修或被下游依赖的现场；不轮询未来 review、不创建后台监听或定时任务。

用户告知“已提交 Submit review”“按 review comments 处理”等后，沿原任务和 PR 读取最新实际 review、行内评论、对应提交及当前差异；这些后续指令已授权核实并处理本任务内的评审问题，无须再问是否开始修复。仅告知 review 已提交不代表批准或人工验收通过；Pending、Comment、Request changes、Approve 依据真实内容分别判断，平台审批仍不自动替代项目要求的业务验收。

逐项核实评论与有效需求：确认的缺陷在原分支／PR 修复，补充适用测试并复验；有证据的误报或已过时评论说明依据；会实质扩大目标或改变验收的建议只就变化项取得决定，不自行接受新范围。新提交后复核受影响审查、人工验收和 CI 证据；若修复改变前置契约，同步核对依赖它的下游。完成本轮约定修复和 PR 更新后，再报告并等待；不因收到评论而自动获得合并授权。

评论读取、代码修复和在远端代用户回复／提交 review 是不同操作，后者仍须有明确发送授权。工具无法读取评论时说明实际缺口，请用户提供评论内容，保留其余已完成成果，不臆造 review 结论。

## 本地回合并路径

仅在本轮明确要求本地回合并时适用；本地提交后等待的默认路径不执行本节。由主 agent 按“本地提交 → rebase 到最新目标 → 验证 → 目标快进更新”交付，同时更新主仓库目标分支及工作区。使用 Git 提交级整合，不复制文件覆盖主仓库，也不默认创建 merge commit。无需逐次询问是否提交或回合并；用户明确只要补丁、不提交、不合并或项目有明确交付流程时沿用其要求。本地回合并不包含自动推送、远端 PR 合并、部署或发布。

## 开始时定位目标

记录目标仓库、原始工作区绝对路径、目标分支及起始提交。优先沿用用户或项目明确的目标；没有另行指定时，使用启动任务的原始工作区当时所在的本地分支，不猜测固定名为 main 或 master，也不把远端地址当成本地目标。目标处于 detached HEAD 或存在多个有效目标时，先查已有任务与交接；仍无法确定则只暂停回合并，继续不依赖该选择的开发。

入口已是任务专属 worktree 时，从宿主创建来源或已有交接定位原主工作区及目标分支，沿用已记录目标，不能把任务分支自身当作回合并目标。任务跨会话续做不改变回合并目标，也不因此新建 worktree。缺少来源时先核实仓库 worktree 信息，仍不能确认则报告具体缺口。

记录任务 worktree、任务起始输入与带入的已有修改。只提交本次任务改动，使用明确文件或选定差异暂存，不把用户已有修改、他人工作、缓存和验证工件顺手提交。本次实现若依赖尚未提交且无法分离的已有修改，说明具体依赖并保留结果，不能代用户提交这些内容。

## 整合并更新主工作区

回合并由任务主 agent 执行，先核实本任务相关子任务已结束，待提交差异完整且相关输入保持稳定。

1. **核实目标与前置状态。** 重新确认目标工作区仍检出记录的目标分支、没有进行中的合并／变基及未提交修改，包括暂存和未跟踪文件；确认任务提交及其验证证据有效。目标不干净时保留其状态，不自动 stash、提交或清理用户工作，标明回合并暂未完成。
2. **Rebase 到最新目标。** 读取当前目标提交；先核实已记录的任务结果（含 rebase 后提交）是否已被目标包含，已包含时核实目标状态与所需验证，直接报告已合并。否则确认待重放序列只包含本任务尚未共享的提交，在任务 worktree 执行 `git rebase --no-autostash <目标最新提交>`。不重放、改写其他任务或已回合并的提交，不强制回退目标；不能确认提交归属时保留结果并报告具体缺口。
3. **验证 rebase 后候选。** 在任务 worktree 处理有明确依据的 rebase 冲突，保存重放前后提交对应关系，按[整合复审触发条件](code-review.md#整合复审触发条件)检查实际差异、接口与受影响回归，完成必要的独立复审和集成验证。无法确定正确解法或检查失败时保留任务结果，目标不动，明确报告未合并。复用证据须核实其对当前候选仍有效，不能直接借用 rebase 前通过。
4. **快进更新目标。** 再次核实目标分支、提交及干净状态，使用普通 Git 安全更新，例如在目标工作区执行 `git merge --ff-only --no-autostash <已验证候选提交>`。目标在检查期间又变化时回到最新目标重新整合并验证，不能强制更新引用、reset 或覆盖文件；持续变化时保留结果并报告暂未合并。
5. **核实完成。** 确认目标分支和工作区实际包含本次结果，在目标状态执行项目要求的合并后检查，记录最终提交、受测状态和结果。合并后检查失败时如实报告“已合并、验证失败”，保留现场并修复，不自动重置目标。

任务在 detached worktree 开发也可使用已保存的候选提交；目标必须是已定位的本地分支与工作区。不能绕过 Git 对其他 worktree、未提交修改或分支状态的保护。

## 本地路径完成判断与恢复

本轮明确要求本地回合并时，完成条件同时包含实现验收和回合并；默认提交后等待时，以约定提交及交付证据判断本轮完成，并保留未合并事实。仅 worktree 测试通过、仅生成补丁或仅创建本地提交时，分别报告实际进度，不能称已合并回主仓库。非 Git 项目按已有文件交付约定处理，不强行初始化 Git 或伪造合并结果。

Rebase 完成后、更新目标之前即保存原任务提交与 rebase 后提交的对应关系。恢复时先核实原目标、该对应关系、目标当前 HEAD、是否已有 rebase 进行中及是否已包含重放后的结果，再继续；不能仅因原提交哈希改变而重复交付。调用超时或中断不能直接重复提交、rebase、快进或删除 worktree。记录“未合并／已合并待检查／已合并且检查通过”等实际状态。确认目标包含结果、必要检查通过、证据已保留且执行者停止后，才按宿主约定回收本任务的临时 worktree；受阻时保留它。

## 关联Issue关闭与现场清理

项目或用户要求Issue收尾时，沿已有任务授权及[Issue用途](../shared/execution-contract.md#issue用途与执行入口)执行。反馈因重复、拒绝或转讨论处理时记录对应决定及关联，不能写成实现完成，也不要求补齐执行AC后才能分诊收尾。

执行Issue不因代码已提交、单个子任务完成或工作区可清理就关闭。先核对完整验收要求、必需检查和交付边界；需要人审或PR合并时确认实际接受记录及全部相关PR已合并。仅交补丁的明确任务按其约定验收，不擅自增加合并义务。多PR／跨仓库任务以Issue完整范围判断，不能提前关闭父Issue。父项还须核对总体验收、必要子项交付及跨子项验证；所有子项已关闭只说明平台状态，取消／延期不能当作目标通过。

保留Issue与PR／提交、验收及测试证据的关联，然后执行关闭并读取实际状态；已自动关闭时仍核实完成条件。仅当合并本身满足所有关闭条件时使用自动关闭关联，否则用普通链接并在条件齐备后关闭。核实项目的父子级联关闭配置，不能用自动状态替代父项总体或子项验收；出现提前关闭时如实报告缺口，沿已有授权纠正状态。取消／放弃须有明确决定并采用对应原因，不写成实现完成。

未完成条目、失败检查或待验收仍存在时保持打开。关闭调用超时／中断先查询再重试；权限或工具不可用时记录待关闭和恢复入口，不声称关闭成功。Issue关闭、本地同步、环境准备及资源清理分别记录；清理因宿主限制受阻不自动否定已完成验收，但Issue明确包含清理验收时须完成该项。清理前确保成果与证据可恢复，关闭不隐含删除数据或发送额外消息／评论的授权。
