# 执行契约与范围控制

## 开始前

结合[输入与证据](input-and-evidence.md)，在现有任务、工作记录或对话中明确下列相关内容；不是必填表或额外审批关卡：

- 本次用户结果、验收行为及来源，包含与排除范围。
- 适用架构、接口／数据契约、兼容和质量约束。
- 实现入口、已有可复用能力、外部依赖与关键未知。
- 可验收切片及顺序、测试入口和已知基线问题。

小任务可用一段话；复杂任务按切片列出实际依赖。没有明确排除项也不扩大为任意优化授权。不要用数据库、后端、前端等文件分组取代可验收结果；必要技术前置工作可以单独成项并说明验证方式。

## Issue用途与执行入口

Issue可管理缺陷、功能、重构、文档、调研和汇总计划。开源项目的公开收件箱还承载未确认的报告、建议和使用问题；反馈可以缺少复现、范围或验收，不能对所有提交强加执行任务标准。沿项目约定分诊、去重和补充信息，区分反馈／待澄清、执行、调研与汇总用途；这些用途不是强制的平台类型、标签或固定状态流。

编码入口为用户明确指定实现的Issue，或在已有授权内由项目任务选择约定纳入本轮执行范围的Issue。公开提交、Open状态、标签、负责人或列入长期计划本身不单独构成本轮实现授权。仅要求整理或评估时交付对应结果；已有明确实现要求时直接沿用，不为类型变更或流程形式追加确认。

反馈经确认后可在原Issue补充范围和完成条件，保留讨论历史并直接转入执行。多个报告汇聚为一项改造，或需独立跟踪实施范围时，可另建执行Issue并关联来源；不要求每条反馈复制一张研发单，不重复维护相同进展。重复、拒绝、转讨论和实现完成分别说明原因，收尾沿[关联Issue关闭](../workflows/delivery-and-closeout.md#关联issue关闭与现场清理)。

执行前核对本次目标与范围、可判断的验收、适用约束和验证入口，以及当前切片的必要依赖。缺口只影响相应部分，无依赖部分继续。任务已创建或获接受不代表这些条件均已具备；状态与分诊结果沿项目已有字段和记录维护，不另建台账。未采用Issue的轻量任务继续沿具体来源，不为通用技能强制引入任务平台。

## 执行依据与追溯

项目采用Issue驱动时，以真实执行Issue及验收要求作为代码、测试和子任务的共同依据，关联有效需求／规范来源、约束、架构与复用入口。Issue承接上游来源，不复制全部规范或取代正式业务正文。结果关联实际实现位置、受测代码状态、环境和证据，勾选或关闭不代替验证。

Issue使用完整URL或带仓库的编号，跨仓库保持唯一定位。小任务可用预期行为、复现／验证步骤及关联PR或交付记录承载追溯，无须新增AC编号或独立快照文件。多人、多PR、跨仓库、长周期或需按条目委派时，沿项目约定保留稳定验收标识、所用内容版本或可追溯快照及覆盖映射；已经建立的标识不重排、不复用，变更记录语义与影响。实现与验证者核实当前要求，发现遗漏先更新依据，主agent不能只用摘要代替原始要求。

代码和测试到Issue／验收的关联可通过PR或既有验证记录表达，同时说明行为、实现或验证方式；是否在代码／测试注释中写编号沿项目规范，不普遍要求嵌入编号。委派时提供Issue定位与有效内容、分配范围、必要规范章节、工作区基线、接口及修改边界；同一行为的测试、实现和回归由同一执行者完成。实现后补充主要位置、方式与必要取舍。

真实Issue创建、更新和关系调整按已有授权，调用结果不明先查询实际内容及关系，避免重复建单；不可用时保留待登记或待关联，不伪造ID或声称已建立远端任务。

## Issue建立与大小检查

建立或拆分前检查已有Issue是否覆盖同一目标，按独立跟踪需要选择组织方式：

| 组织方式 | 适用情形 |
|---|---|
| Issue正文清单 | 同一结果中的紧密步骤，共享责任与交付节奏，无须独立跟踪 |
| sub-issue | 属于父目标，需要独立负责人、验收、排期或阻塞状态 |
| 独立Issue及依赖／关联 | 有自己的生命周期，或作为多个目标共用的前置工作 |
| 项目／里程碑 | 聚合多个目标、跨迭代计划，沿项目已有组织方式使用 |

单个执行Issue应有一个可独立验收与交付的结果，能列清范围、依赖及相关回归；此粒度要求只适用于执行项，不约束原始反馈或汇总项。交付可以是行为结果、经验证的技术前置产物，或调研结论，不要求每项独立上线。具体条目数量、规模提示与PR映射由项目规定。多个结果可以分别验收、延期或交付时拆分；同一行为所需的实现、测试、文档和拒绝／恢复场景保持闭环，不按技术层、文件数、agent或聊天划分Issue。跨模块或跨仓库不是自动拆分理由，也不是无限扩大范围的理由；单个结果确需多PR时明确整体交付与关闭条件。

关键未知可能改变目标时先界定调研问题、证据要求和停止条件；调研完成不代表功能完成或后续实现已获授权。独立子项存在依赖时明确前置及解除条件。汇总Issue保留总目标、子项和整体验收，执行者绑定所负责的具体子Issue及验收。规模阈值只按项目规则使用，不通过合并验收条目、降低验证或机械拆碎来满足数量。

建立前、范围扩大和恢复时重新判断。拆分已有Issue保留原编号与历史语义，记录旧条目到子项的映射，更新受影响的委派、PR及后续实现／测试定位；不得靠移除未完成条目宣称完成。新建或调整远端Issue沿已有授权，不因本节自动批量重组既有任务；父子项各按自身完整验收和交付条件关闭。

## 父子Issue与设计交接

采用Issue管理的项目，复杂目标由父Issue表达有边界的总范围、总体验收及子项覆盖，执行型sub-issue承接一个可交付结果。简单目标可以只有一个执行Issue，不为形式强制父子两层。父子关系表达目标归属，dependency（blocked by／blocking）表达前置或阻塞，Issue与PR的关联表达实现范围；三种关系分别记录，父子关系不表示先后顺序。父子关系与执行／调研／汇总用途分开，继续分层须能改善独立验收或责任划分。

使用项目平台支持的实际父子及依赖关系并回读确认；只有标题或正文链接不等于已建立原生关系。不支持时明确等价关联或待建立状态，不扩大平台权限。共享前置只建一次，相关消费者引用依赖，不因不同父目标重复建单。开始受影响工作前核实依赖要求的契约、产物或决定实际可用，不只看前置是否关闭；阻塞时说明原因、解除条件和下一步，无依赖部分可继续。

父范围到子项验收的映射要能检查遗漏与重叠，子项延期、取消或新增时复核父范围与总体判据；不把“全部子项关闭”或平台级联状态直接当作父目标完成。

接收设计时从所分配执行Issue及其条目进入，只补读父项的总体边界和适用约束，再定位有效需求、设计及规范章节。简单需求不要求先有独立故事或另建研发／测试任务；复杂场景可保留总览。长期规则留项目权威正文，执行AC、进展与PR／测试证据关联留Issue；既有故事／文档AC／工作包编号保留来源版本及映射，不与Issue内编号混用，不复制第二套实时状态。

## 适用规范与读取预算

先从项目指令、已有规范索引或项目上下文定位少量权威正文，按本次目标选章节；只掌握相关需求、约束、实现边界及验收即可开始，不全量读取所有设计、README或技能引用。按[内容归属](project-context.md#技能与项目的内容归属)区分通用方法、项目工程规则与业务依据；编码规范和组件文档从项目代码入口定位，不假定都在需求目录。文件归并后使用当前正文，历史迁移入口不加入必读集合。项目没有集中入口时从实际材料定位，不强制先整理文档才能编码。

在已有任务记录中简要保存“条目及来源／有效版本 → 适用行为与实现位置 → 检查方式与状态”。按任务考虑注释与需求定位、类型、对象／状态、依赖、配置、目录、测试以及界面／组件规则；具体内容与强度来自项目，不把这些类别当成每个项目必须采用同一架构。小任务几行即可，不复制规范全文或增加用户审批。

只跟随影响本次决定的引用。原文已读且相关输入未变时复用记录；触及新边界、来源变化、用户纠正或恢复时回读受影响章节。未决需求与“未读到规范”分开处理，不能用上下文压缩作为遗漏强制要求的理由。

切片后对照实际差异标注符合、不符合、未验证或不适用（说明理由）。记录检查位置或实际工具证据；“已阅读”“测试通过”不能替代符合性。审查者独立检查条目遗漏，不能只审核作者挑选的清单。已确认的必需项未满足时继续修复或如实交付受限范围，不能自行将强制项降为建议。

## 改动与计划的关系

每项实质改动必须满足本次验收或其必要技术支撑。预计文件清单是定位和影响判断依据，不是禁止发现真实依赖的白名单。

| 发现 | 处理 |
|---|---|
| 需要修改未预计的关联模块 | 核实调用与契约关系；在已授权任务内补充计划、测试和影响后继续 |
| 发现无关缺陷或优化机会 | 简要记录，保持本次范围；不顺手重写、统一风格或升级依赖 |
| 当前实现不满足有效架构 | 在本次影响范围纠正；涉及更大架构取舍时定位缺口，不默默绕行 |
| 环境失败诱使采用另一条链路 | 先判断替代是否仍满足任务与架构；缩减验证时明确边界，不能将绕行结果当作目标完成 |
| 用户明确改变目标或规则 | 更新本次有效依据、切片、约束和测试影响，不继续执行旧计划 |
| 新事实推翻设计前提 | 提供证据及替代选择；可自主解决的实现选择继续，需业务取舍的部分保持待决 |

不要为了减少文件数隐藏必要修改，也不要把“顺便清理”包装为技术前置。新增框架、公共组件或依赖须有当前任务与实际收益依据。

## 检查时点

开始前核对输入与范围；每个切片完成后核对实际改动；交付前检查整体差异。出现目标变更、关键证据变化、意外大范围修改或中断恢复时立即复核。

每次核对回答：是否仍实现有效目标？是否引入未委托能力？是否绕过架构或重复实现？测试是否检验当前定义？下一步是否有明确完成条件？只记录有变化的决定和缺口，避免反复生成全套报告。

发现自身新增的无关改动时，只移除可确认属于自己的无关部分，保留用户和他人的修改。归属不明时先检查差异，不执行整体回滚或重置。

## 继续与停止

在已授权范围内连续推进，不为测试、普通修复或每个切片追加确认。仅暂停依赖未决业务取舍、明确权限限制或不可用关键条件的工作，并说明具体影响。没有阻塞依据不能因流程步骤未齐而停止；存在关键缺口也不能把任务标为完成。
