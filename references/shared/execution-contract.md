# 执行契约与范围控制

## 开始前

结合[输入与证据](input-and-evidence.md)，在现有任务、工作记录或对话中明确下列相关内容；不是必填表或额外审批关卡：

- 本次用户结果、验收行为及来源，包含与排除范围。
- 适用架构、接口／数据契约、兼容和质量约束。
- 实现入口、已有可复用能力、外部依赖与关键未知。
- 可验收切片及顺序、测试入口和已知基线问题。

小任务可用一段话；复杂任务按切片列出实际依赖。没有明确排除项也不扩大为任意优化授权。不要用数据库、后端、前端等文件分组取代可验收结果；必要技术前置工作可以单独成项并说明验证方式。

## Issue用途与执行入口

Issue可管理缺陷、功能、重构、文档、调研和汇总计划。开源项目的公开收件箱还承载未确认的报告、建议和使用问题；反馈可以缺少复现、范围或验收，不能对所有提交强加执行任务标准。沿项目约定分诊、去重和补充信息，区分反馈／待澄清、执行、调研与汇总用途；这些用途不是强制的平台类型、标签或固定状态流。

本次任务以Issue作为执行依据时，编码入口为用户明确指定实现的Issue，或在已有授权内由项目任务选择约定纳入本轮执行范围的Issue。公开提交、Open状态、标签、负责人或列入长期计划本身不单独构成本轮实现授权。仅要求整理或评估时交付对应结果；已有明确实现要求时直接沿用，不为类型变更或流程形式追加确认。

反馈经确认后可在原Issue补充范围和完成条件，保留讨论历史并直接转入执行。多个报告汇聚为一项改造，或需独立跟踪实施范围时，可另建执行Issue并关联来源；不要求每条反馈复制一张研发单，不重复维护相同进展。重复、拒绝、转讨论和实现完成分别说明原因，收尾沿[关联Issue关闭](../workflows/delivery-and-closeout.md#关联issue关闭与现场清理)。

执行前由执行者核对目标、成功判据、约束、粒度与前置产物；核对是读取和判断，不是要求用户再批准一次。已获实现授权且 Issue 已明确的验收条件直接作为本轮依据，不因进入执行、改写为测试清单、拆分委派或恢复会话重复确认。“执行项”名称或获接受仍不代替对实际缺口的判断。多个可分别交付结果重新切分或按汇总项接收；关键行为未定标明问题及受影响部分；规模缺乏依据补必要调查。已有授权内可解决的直接处理，只询问缺失的业务决定；无依赖部分继续，尚有关键缺口不标为整体就绪，不新增审批或台账。

是否以Issue为执行依据按本次任务及项目约定判断，仓库启用Issues或用其接收社区反馈不意味着所有修改必须建单。本次未采用Issue时沿有效用户请求或已有任务来源执行及恢复；项目明确要求关联Issue时，按既有授权查询复用或登记执行项。不因任务较小跳过项目要求，也不因通用技能引入额外建单义务或重复确认。

## 执行依据与追溯

本次任务以Issue作为执行依据时，以真实执行Issue及验收要求作为代码、测试和子任务的共同依据，关联有效需求／规范来源、约束、架构与复用入口。Issue承接上游来源，不复制全部规范或取代正式业务正文。结果关联实际实现位置、受测代码状态、环境和证据，勾选或关闭不代替验证。

Issue使用完整URL或带仓库的编号，跨仓库保持唯一定位。小任务可用预期行为、复现／验证步骤及关联PR或交付记录承载追溯，无须新增AC编号或独立快照文件。多人、多PR、跨仓库、长周期或需按条目委派时，沿项目约定保留稳定验收标识、所用内容版本或可追溯快照及覆盖映射；已经建立的标识不重排、不复用，变更记录语义与影响。实现与验证者核实当前要求，发现遗漏先更新依据，主agent不能只用摘要代替原始要求。

代码和测试到Issue／验收的关联可通过PR或既有验证记录表达，同时说明行为、实现或验证方式；是否在代码／测试注释中写编号沿项目规范，不普遍要求嵌入编号。委派时提供Issue定位与有效内容、分配范围、必要规范章节、工作区基线、接口及修改边界；同一行为的测试、实现和回归由同一执行者完成。实现后补充主要位置、方式与必要取舍。

真实Issue创建、更新、关系及元数据调整按已有授权，调用结果不明先查询实际内容、关系及字段，避免重复建单；部分成功保留真实映射，只补缺失项，不伪造ID或声称全部落地。

### 平台元数据

采用任务平台时按项目规范核对 Labels、Type、Fields、Projects 的用途与实际配置；这些信息用于分类、排期和跟踪，不替代正文、验收或执行授权。没有配置且本轮要求建立约定时，根据实际工作设计最小方案，再在已授权范围落实，不以默认选项代表已确认政策；仅接收任务不自行治理平台。

- **Labels 与 Type：** 按本项工作性质选择真实类型，标签表达项目约定的筛选维度。父子用途不等于平台类型，不机械继承父项全部标签，不用标题前缀或同名标签冒充 Type。没有适用标签可以为空。
- **Fields：** 区分组织级 Issue 字段与 Project 自定义字段，核实所属对象、字段类型、选项和当前值；同名不表示同一字段，Issue 表单正文也不等于原生字段。按有效决定或项目估算口径填值，未知优先级、日期或估算不套默认值；不将前置顺序当作业务优先级。
- **Projects：** 使用项目指定看板，逐项核实成员关系和实际进度，父项入板不代表子项已入板。状态依据当前工作及交付条件；建单不标进行中，前置关闭不标就绪，测试通过不标已完成。阻塞关系和解除条件保留在任务中，不靠状态标签替代。

创建、接收、拆分及交付时核对本次受影响的信息；执行中的状态变化按[任务状态与进度](../workflows/task-progress.md)同步并回读，不留到收尾补记。已知且按约定应填的值须设置；必填决定缺失时只澄清变化项，可选未知保留为空。更新仅触及本次负责字段，保留无关值和已有项目成员关系；项目未要求时不复制一套元数据到正文。关闭后回读相关看板状态，取消不冒充完成。权限不足、字段不可见与确实未配置分别报告；继续无依赖工作，必需设置未落地时不称登记完成，不自行提权、创建字段或重配看板。

## 从目标需求进入实现

本次采用 Issue 时，从项目指令、规范索引或已有上下文的 `standards` 定位平台字段、编号和规模参数；执行、拆分、状态与交付规则由本技能维护，不要求项目另建流程规范。

先读本次执行项的目的、目标能力或行为、范围和成功标准，再查相关代码、测试及父项约束。技术重构也要理解目标职责和协作关系，不能把“移动文件、提取 Hook”当成全部需求；原代码用于了解现状，不自动定义正确目标。已定契约与强制设计继续遵守，普通文件拆法和组件选择由执行阶段确定。

将目的与 AC 转成测试场景及预期，沿用已明确的结果判据和既有确认；不为这份派生清单再增加一次用户确认。正常路径、边界、失败及回归用例的补充，只要不改变目标、范围和预期，由执行者自主完成。仅缺失的业务决定、相互冲突的要求或实质改变范围／预期的部分需要用户决定，无依赖部分继续；不要求预先写好实施方案。任务有明确的额外测试审批要求时，只对其指定范围核对已有批准，不由项目另建重复流程或从检查清单推导审批；接受记录与授权按[交付规则](../workflows/delivery-and-closeout.md#pr-阶段与人工验收)核实。退役、迁移或替换时核对消失、保持及受影响存续能力的预期结果，“最小适配”不是行为决定，“记录回归结果”不是通过判据。只补影响本项的缺口，不自行发明业务规则。

迁移回归时区分正式入口可达行为、模型／组件能力和替身数据证明范围，沿有效规则决定预期；不把旧演示行为直接搬入正式场景，也不为测试补齐未授权的真实集成。跨主题用例按各自断言明确归属，共用场景不等于多项重复负责。退役验收包含专用实现或资源移除时，验证约定对象实际退出且存续消费者无悬空依赖；入口不可达不能替代移除，未完成的前置迁移仍由原责任项承接。

实施与交付同时核对原始目的、全部验收及实际结果：测试全绿或代码动作完成不能证明目的已达成。发现遗漏时补足有效依据及验证，不用当前实现或测试反过来缩减目标。

## Issue建立与大小检查

建立或拆分前读取项目任务平台配置并检查同一目标是否已有任务。正文先表达问题、目的、完成后的能力／行为，再给验收、范围、约束和依据；代码入口与建议方案作为必要补充，不把现有代码行为逐项翻译为目标，也不复制通用执行流程。按独立跟踪需要选择组织方式：

| 组织方式 | 适用情形 |
|---|---|
| Issue正文清单 | 同一结果中的紧密步骤，共享责任与交付节奏，无须独立跟踪 |
| sub-issue | 属于父目标，需要独立负责人、验收、排期或阻塞状态 |
| 独立Issue及依赖／关联 | 有自己的生命周期，或作为多个目标共用的前置工作 |
| 项目／里程碑 | 聚合多个目标、跨迭代计划，沿项目已有组织方式使用 |

单个执行Issue应有一个可独立验收与交付的结果，能列清范围、依赖及相关回归；此粒度要求只适用于执行项，不约束原始反馈或汇总项。交付可以是行为结果、经验证的技术前置产物，或调研结论，不要求每项独立上线。AC 每项应有可观察、可判断的结果；重构应说明责任与消费者迁移、兼容要求及旧入口退出条件，文件移动或数量不能单独证明完成，不设通用数量；规模提示读取项目参数，PR 映射按本技能交付规则。多个结果可以分别验收、延期或交付时拆分；同一行为所需的实现、测试、文档和拒绝／恢复场景保持闭环，不按技术层、文件数、agent或聊天划分Issue。跨模块或跨仓库不是自动拆分理由，也不是无限扩大范围的理由；单个结果确需多PR时明确整体交付与关闭条件。

同一总目标不等于同一执行项。对多结果或预计过大的任务，检查某部分能否先验证、其余延期后是否仍保有有效成果，不按 AC 编号切分。A 有可检验产物、B 消费它时可以分项并明确解除条件。主张必须同项时说明拆开会破坏的具体契约或不可接受的中间状态，以及为何无合理可验收阶段；“耦合”“完整结果”不足以证明。循环依赖重划边界，共享前置只维护一次。按代码、测试基础和未知复核工作量；零碎步骤并入所属结果，独立小缺陷不扩大，不减少必要验证。

关键未知可能改变目标时先界定调研问题、证据要求和停止条件；调研完成不代表功能完成或后续实现已获授权。独立子项存在依赖时明确消费的契约／产物、版本或定位及可用判据；仅共享文件或同属一个清理目标不自动构成阻塞。汇总Issue保留总目标、子项和整体验收，执行者绑定所负责的具体子Issue及验收。既有子项仍过大可保留编号转为汇总，再拆执行项，不强制新增层级或固定拆分数量。规模阈值只按项目规则使用，不通过合并验收条目、降低验证或机械拆碎来满足数量。

建立前、范围扩大和恢复时重新判断。拆分已有Issue保留原编号与历史语义，记录旧条目到子项的映射，更新受影响的委派、PR及后续实现／测试定位；不得靠移除未完成条目宣称完成。新建或调整远端Issue沿已有授权，不因本节自动批量重组既有任务；父子项各按自身完整验收和交付条件关闭。

## 父子Issue与设计交接

采用Issue管理的项目，父项与执行子项不套同一详细模板：父项表达整体问题、目的、总范围、整体验收、子项覆盖和未拆分范围，不复制子项实现与实时状态；执行型sub-issue表达本次目标需求、范围、成功结果、必要约束、依赖产物及验证方式，承接一个可交付结果。简单目标可以只有一个执行Issue，不为形式强制父子两层。父子关系表达目标归属，dependency（blocked by／blocking）表达前置或阻塞，Issue与PR的关联表达实现范围；三种关系分别记录，父子关系不表示先后顺序。父子关系与执行／调研／汇总用途分开，继续分层须能改善独立验收或责任划分。

使用项目平台支持的实际父子及依赖关系并回读确认；只有标题或正文链接不等于已建立原生关系。不支持时明确等价关联或待建立状态，不扩大平台权限。共享前置只建一次，相关消费者引用依赖，不因不同父目标重复建单。开始受影响工作前核实依赖要求的契约、产物或决定实际可用，不只看前置是否关闭；阻塞时说明原因、解除条件和下一步，无依赖部分可继续。

父范围到子项验收的映射要能检查遗漏与重叠，子项延期、取消或新增时复核父范围与总体判据；不把“全部子项关闭”或平台级联状态直接当作父目标完成。

接收设计时从所分配执行Issue及其条目进入，只补读父项的总体边界和适用约束，再定位有效需求、设计及规范章节。简单需求不要求先有独立故事或另建研发／测试任务；复杂场景可保留总览。长期规则留项目权威正文，执行AC、进展与PR／测试证据关联留Issue；既有故事／文档AC／工作包编号保留来源版本及映射，不与Issue内编号混用，不复制第二套实时状态。

## 父Issue执行与依赖调度

父 Issue 的执行范围包括已纳入交付的执行子项及必要联合验证。子项进入实现须具备明确范围、验收条件和实施授权；纯汇总、范围未定及仅分析的任务不进入编码。采用[父集成分支与子 PR](../workflows/delivery-and-closeout.md#父issue集成分支与子pr)组织：独立子项从父分支开发并 PR 回父分支，最后以主 PR 承接完整目标到主线。先核实子项、实际依赖和可用产物，再决定启动顺序；父子层级、列表顺序、编号和平台状态不决定先后，已有验收条件在各子项执行中直接沿用。

- 无前置阻碍、接口清楚且写入和运行资源可隔离的子项并发推进。一个子项进入待 review／人工验收，不阻塞其他可推进子项；不把每项验收、关闭或 PR 合并作为启动下一项的统一门槛。工具或资源不支持并发时可顺序执行，说明实际限制。
- 代码依赖已在前置 PR 中形成可用、可定位且经过相关检查的产物时，从该 PR 的确定提交建立下游独立分支／工作区；无需一律等前置人工验收或合并。分支、PR 目标及基线变化按[依赖 PR 开发](../workflows/delivery-and-closeout.md#依赖pr上的分支开发)处理。多个前置须核实实际组合，不能仅靠分支继承声称依赖全已具备。
- 依赖要求真实发布、迁移、外部决定或尚未存在的契约时，仅分支出代码不能解除阻塞；保留原因与可用判据，只暂停受影响部分。共享前置由一个责任方维护，高耦合或循环依赖先收敛契约与边界。
- 依赖改动后复核受影响下游的范围、基线、接口与证据。允许提前开发不等于提前验收；各子项仍独立满足交付条件，父项仍核对整体覆盖与跨项验证。
- 主 Issue 尚未整体验收时，sub-issue 只承担自身 AC、必要约束、直接受影响契约与相关回归，不把主目标的全量系统验收复制到每个子项／PR。主 Issue 在本轮必要实现整合到稳定候选后，统一承担跨子项联合验证和约定全量验收；验收范围、候选版本和证据归属要明确，可复用仍有效的子项证据，不逐项重跑无变化用例。各子项通过或关闭不代表主项通过，主项全量尚未执行也不单独阻塞已满足自身条件的子项交付或其他就绪项。公共契约等变化确实影响本项依赖时仍补必要检查，不能把自身已知风险一概转交主项；主项通过后再变化须复核相关旧结论。

父任务在首批代表性切片形成后，按[跨项风险前置](../workflows/verification.md#跨项风险前置)验证共享边界，不把所有组合风险留到最终全量。

父任务的开发交付包括约定子项实现、验证、父分支整合及主 PR。交付记录分别列明子项状态、主项全量结果、待评审内容和阻塞，并按[等待与反馈规则](../workflows/delivery-and-closeout.md#提交后的等待与评审反馈)进入待反馈状态。单个子项待评审不结束其他已授权且可推进的工作；阻塞项保留恢复条件，不扩展未授权范围。

## 适用规范与读取预算

先从项目指令、已有规范索引或项目上下文定位少量权威正文，按本次目标选章节；只掌握相关需求、约束、实现边界及验收即可开始，不全量读取所有设计、README或技能引用。按[内容归属](project-context.md#技能与项目的内容归属)区分通用方法、项目工程规则与业务依据；编码规范和组件文档从项目代码入口定位，不假定都在需求目录。文件归并后使用当前正文，历史迁移入口不加入必读集合。项目没有集中入口时从实际材料定位，不强制先整理文档才能编码。

在已有任务记录中简要保存“条目及来源／有效版本 → 适用行为与实现位置 → 检查方式与状态”。按任务考虑注释与需求定位、类型、对象／状态、依赖、配置、目录、测试以及界面／组件规则；具体内容与强度来自项目，不把这些类别当成每个项目必须采用同一架构。小任务几行即可，不复制规范全文或增加用户审批。

只跟随影响本次决定的引用。原文已读且相关输入未变时复用记录；触及新边界、来源变化、用户纠正或恢复时回读受影响章节。未决需求与“未读到规范”分开处理，不能用上下文压缩作为遗漏强制要求的理由。

切片后对照实际差异标注符合、不符合、未验证或不适用（说明理由）。记录检查位置或实际工具证据；“已阅读”“测试通过”不能替代符合性。审查者独立检查条目遗漏，不能只审核作者挑选的清单。已确认的必需项未满足时继续修复或如实交付受限范围，不能自行将强制项降为建议。

## 改动与计划的关系

每项实质改动须对应本次目标、验收或有实际依赖依据的必要支撑。支撑必要不等于必须同项：有用途、可检验的前置产物按上述粒度判断，不可分的支撑随本项完成；新增支撑明显增加工作量时重核边界。文件清单不是修改白名单，父项、兄弟任务、引用或测试中的其他能力不自动进入本项，扩大回归不授权重构被测模块。

| 发现 | 处理 |
|---|---|
| 需要修改未预计的关联模块 | 核实依赖与粒度后补充计划、测试和影响；普通适配随所属结果完成 |
| 本次改动引入回归 | 在本项修复并复验，不以范围控制推迟自身引入的问题 |
| 发现既有独立缺陷或优化机会 | 记录具体发现及影响，按授权关联或另建后续项；不顺手重写、统一风格、补未来能力或升级依赖 |
| 必要前置或方案实质改变目标、公共契约、范围或验收 | 说明原因、影响和选择；已有有效决定沿用，否则只就变化项取得用户决定，再推进受影响部分；同步覆盖、依赖，并核对直接受影响任务正文的目标、验收和验证前提；未复核如实标明，无依赖部分继续 |
| 当前实现不满足有效架构 | 在本次影响范围纠正；涉及更大架构取舍时定位缺口，不默默绕行 |
| 环境失败诱使采用另一条链路 | 先判断替代是否仍满足任务与架构；缩减验证时明确边界，不能将绕行结果当作目标完成 |
| 用户明确改变目标或规则 | 更新本次有效依据、切片、约束和测试影响，不继续执行旧计划 |
| 新事实推翻设计前提 | 提供证据及替代选择；可自主解决的实现选择继续，需业务取舍的部分保持待决 |

不要为了减少文件数隐藏必要修改，也不要把“顺便清理”包装为技术前置。新增框架、公共组件或依赖须有当前任务的必要性与实际收益依据；局部任务不自动授权全局治理。拆出或延期的要求保留承接和有效决定，不自行降低验收。目的及完成条件满足后收敛交付，不继续寻找额外工作。

## 新发现的归属

先区分本次引入的回归、原验收遗漏、既有独立缺陷和新需求，再决定修复归属。仅在当前整合分支复现，不能证明由本次改动引入；有争议且影响范围决定时，在原目标基线与当前候选用相同最小场景对照，记录代码、环境及结果，无法复现时保留不确定性。

本次回归必须修复；有效验收明确覆盖的遗漏仍在本轮范围，不因原基线也失败而豁免。既有独立缺陷或新能力沿前表承接，不借“跨项修复”自动扩大。若必要修复实质扩大目标或改变已定行为，只暂停依赖该决定的部分。分类、依据和决定保留在原任务／发现记录，不另建第二份范围台账。

## 检查时点

开始前核对输入与范围；每个切片完成后核对实际改动；交付前检查整体差异。出现目标变更、关键证据变化、意外大范围修改或中断恢复时立即复核。

每次核对回答：是否仍实现有效目标？是否引入未委托能力？是否绕过架构或重复实现？测试是否检验当前定义？下一步是否有明确完成条件？只记录有变化的决定和缺口，避免反复生成全套报告。

发现自身新增的无关改动时，只移除可确认属于自己的无关部分，保留用户和他人的修改。归属不明时先检查差异，不执行整体回滚或重置。

## 继续与停止

在已授权范围内连续推进，不为测试、普通修复或每个切片追加确认。仅暂停依赖未决业务取舍、明确权限限制或不可用关键条件的工作，并说明具体影响。没有阻塞依据不能因流程步骤未齐而停止；存在关键缺口也不能把任务标为完成。
