## 问题 1：API 绕过服务公开取消接口，违反明确的责任边界

- **位置：** `review/project/order_app/api.py:11` 直接调用 `self.service._store.get`，`:12–17` 重复权限与状态规则，`:18` 直接调用 `self.service._store.save`。
- **要求依据：** 《项目说明.md》要求“订单状态、权限和重复请求规则由 OrderService 承担”“API 只能通过服务公开接口完成取消，不导入存储、不访问服务私有属性；存储读写由服务负责”。已有的 `OrderService.cancel`（`order_app/services.py:11–21`）完整提供该能力，且基线回归通过。
- **成立条件：** 通过当前 `OrderAPI.cancel_order` 处理任何请求时均直接访问服务私有存储；成功取消 open 订单时直接保存，整个流程从未调用公开的 `OrderService.cancel`。
- **可观察后果：** 原有服务边界检查由基线通过变为失败；独立运行时检查观察到成功取消并保存后，公开服务方法调用次数为 0，证明取消并未经过要求的服务入口。状态、权限及重复请求规则目前有两份实现，服务不再是 API 取消规则的唯一责任位置。
- **实际证据：**
  - `baseline-suite.log`：7 项全通过，退出码 0。
  - `current-suite.log`：13 项中 12 项通过，`test_api_uses_public_service_boundary` 失败，错误为“入口不访问其他对象的私有属性”，退出码 1。
  - `independent-acceptance.log`：`test_api_delegates_to_real_public_service_method` 失败，实际输出 `Expected 'cancel' to be called once. Called 0 times.`。该检查包装真实服务方法而不替换业务规则；同一用例也观察到正确响应与一次实际保存。
- **归属：** 本次引入；基线 API 是尚未接入的入口，没有私有存储访问。
- **修复方向：** 入口调用现有 `self.service.cancel(order_id, actor_id)`，仅将返回的订单投影为约定字典；移除入口中的存储访问和重复业务规则，无需修改已满足要求的服务。
