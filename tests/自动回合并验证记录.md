# 自动回合并验证记录

日期：2026-10-30（Asia/Shanghai）。用户要求会话专属 worktree 开发完成后自动合并回主仓库，并进一步指定采用 rebase。本轮将“本地任务提交 → rebase 到最新目标 → 验证 → 目标快进更新”及合并后检查加入默认完成条件。会话内共享 worktree 和按需使用运行资源的规则保留。

## 规则与被测状态

新增[自动回合并方法](../references/workflows/回合并.md)，同步技能入口、会话工作区、验收、恢复、自动检查和交接。默认目标为任务启动时记录的原始本地分支与工作区，不固定为 main；已有会话 worktree 恢复时核实原目标，不将会话分支自身当成目标。只有本地回合并为默认步骤，远端推送、PR、部署与发布不随之执行。

新版本通过[技能文件摘要](验证证据/自动回合并/技能快照.json)定位；本目录没有 Git 元数据，本次未为它初始化 Git。所有 Git 操作和分支更新只发生在隔离临时夹具。[完整工件](验证证据/自动回合并/完整工件.tar.gz)保留修改前材料、模型被测技能快照、夹具、命令与输出。

## 可运行机制演练

[回合并场景](验证证据/自动回合并/回合并场景.py)使用真实 Git worktree、真实提交和 POSIX 进程锁，实际运行 8 项，均通过：

| 场景 | 实际核对 |
|---|---|
| 干净目标正常完成 | 目标分支及检出文件更新到候选提交，工作区干净 |
| 两个进程并发完成 | 通过同一仓库级锁排队，后者 rebase 到最新目标，保留双方结果和重放后提交，新增历史不产生 merge commit |
| 双方修改同一行 | 冲突保留在会话 worktree，目标提交与文件不变 |
| 目标含用户未保存／未跟踪内容 | 不 stash、不提交、不覆盖，目标及用户内容保持原样 |
| 实际候选验收失败 | 不推进目标分支，保留会话结果 |
| Rebase 改变提交后再次执行 | 根据重放后提交确认已包含结果，不因原哈希变化产生重复提交或交付 |
| 目标工作区切换了分支 | 不静默合并到新分支 |
| 合并后检查才失败 | 报告已合并但验证失败，不自动重置目标 |

这些是维护者的机制演练，不是生产自动合并工具，也不证明模型总会选择相同命令。原始输出及检查退出码保存于[维护检查](验证证据/自动回合并/维护检查.json)。

## 独立编码行为演练

首轮从无实现会话历史的新上下文启动 agent `01a18a9e-ae36-77a2-aaa7-43de7a53b792`，只提供固定技能入口、临时源项目、原始函数需求和允许的副作用范围。任务为实现整数翻倍函数，初始入口为 `NotImplementedError`；原始分支命名为 `delivery-target`，没有名为 main 的目标。请求不额外提示目标实现或预期合并结论；允许按技能规定创建 worktree、本地任务提交及更新临时目标，不允许联网、推送或修改全局配置。

首轮模型实际创建专属 worktree，执行 RED（退出 1）、GREEN 和完整回归后本地提交；持仓库级锁快进更新原始 `delivery-target`，合并后 4 项测试通过，主工作区干净，并回收其临时 worktree。维护者核对最终提交为 `e15fbd4a1d26c562f0c5ba11d1bf0082e2434448`，仅改动实现及新增测试，原始材料保留。记录见完整工件中的 `agent-evidence/` 与 `维护者核对.json`。

首轮模型读取启动时冻结的 `skill/`，当时用户尚未指定 rebase，且目标没有前进；该轮证明自动提交、实际回合并与检查，不能用来证明重放分歧提交。用户指定 rebase 后固定新的 `rebase-skill/`，不让执行中的模型默默切换规则。最终技能与两阶段模型被测快照分别保存。

第二阶段由新上下文 agent `01a18aa7-d4a9-7b01-995f-c424e3b5d4e1` 接手已创建的会话 worktree，实现整数三倍函数。夹具在创建 worktree 后先向原目标提交另一会话的 notes 更新，使会话与目标实际分歧；原始目标和起始状态作为交接材料提供，不提示实现答案。

- 任务原提交为 `c279c96541449abc9d9b00f1a9349007ac7f9bde`，实际持锁执行 rebase 后变为 `0150ff75201f3b704cf4409e665bb202ab4e2dec`，对应关系在目标更新前保存。

- 主工作区和会话 worktree 的 Git 状态均干净；另一会话的 notes、原有测试及项目材料保留；本次只增加实现与对应测试。
- 实际执行的持锁源码保存在完整工件的 `rebase-evidence/deliver.py`，Git 命令、退出码、RED/GREEN、提交映射及检查结果同目录保存。维护者另行核对结果见[rebase 交付核对](验证证据/自动回合并/rebase交付核对.json)。

## 结论边界

机制演练覆盖 M-15 至 M-18 的本地合并、串行协调、保留失败现场与幂等行为。没有验证真实远端仓库、平台保护规则、所有操作系统或两个真实模型同时自动回合并。Git worktree 仍由宿主或实际 Git 能力提供，Markdown 规则本身不构成权限隔离、事件钩子或后台自动化。
